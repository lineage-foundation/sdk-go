# Lineage SDK (Go)

Go SDK for the Lineage `/v1` REST API: a keyless read `Client` plus a keyed `Wallet`
for BIP39/BIP32 key derivation, transaction signing, and submitting payments and item
assets.

## Installation

```bash
go get github.com/lineage-foundation/sdk-go
```

## Quick start

```go
package main

import (
	"context"
	"fmt"
	"log"

	sdkgo "github.com/lineage-foundation/sdk-go"
	"github.com/lineage-foundation/sdk-go/crypto"
)

func main() {
	ctx := context.Background()

	w := sdkgo.NewWallet(sdkgo.Config{
		Mempool: "https://mempool.lineage.to",
		Storage: "https://storage.lineage.to",
		// APIKey is optional; when set it's sent as the x-api-key header on
		// every request.
	})

	// Generate a fresh BIP39 mnemonic and derive the passphrase-encrypted
	// master key. Persist masterKeyEncrypted somewhere safe; on the next
	// launch, reconstruct the wallet with
	// w.FromMasterKey(masterKeyEncrypted, passphrase) instead of InitNew.
	masterKeyEncrypted, err := w.InitNew("a secure passphrase")
	if err != nil {
		log.Fatal(err)
	}
	fmt.Println("master key:", masterKeyEncrypted)

	// Derive the wallet's first keypair.
	kp, err := w.GetNewKeypair(nil)
	if err != nil {
		log.Fatal(err)
	}
	fmt.Println("address:", kp.Address)

	// Check its balance.
	balance, err := w.FetchBalance(ctx, []string{kp.Address})
	if err != nil {
		log.Fatal(err)
	}
	fmt.Printf("balance: %+v\n", balance)

	// Send 100 Token assets to a recipient, sourcing inputs from kp and
	// sending any change back to kp's own address.
	resp, err := w.MakeTokenPayment(ctx, "recipient-address", 100, []crypto.EncryptedKeypair{kp}, kp, 0)
	if err != nil {
		log.Fatal(err)
	}
	fmt.Printf("payment: %+v\n", resp)
}
```

`GetNewKeypair` returns a `crypto.EncryptedKeypair` — the keypair encrypted at rest
under the wallet's passphrase-derived key — not the raw secret key. It, and the
`masterKeyEncrypted` string returned by `InitNew`/`FromSeed`, are what callers persist
between runs. To recover a wallet on a later launch:

```go
w := sdkgo.NewWallet(cfg)
if err := w.FromMasterKey(masterKeyEncrypted, "a secure passphrase"); err != nil {
	log.Fatal(err)
}
// GetNewKeypair(existing) re-derives already-issued addresses deterministically;
// pass the addresses you've already handed out so it skips past them.
kp, err := w.GetNewKeypair(existingAddresses)
```

`Wallet` embeds `*Client`, so every read method on `Client` (`Supply`, `Balances`,
`QueryBalances`, `TransactionStatus`, `LatestBlock`, `BlockByNum`,
`BlockchainEntry`, `SerializeTransactions`, `DeserializeTransactions`, ...) is
available directly on a `Wallet` value too. Use a bare `sdkgo.NewClient(cfg)` instead
of `NewWallet` for read-only use cases that never sign anything.

## Wire compatibility with sdk-js and sdk-python

This SDK is built to be byte-for-byte compatible with
[`sdk-js`](https://github.com/lineage-foundation/sdk-js) (the canonical reference
implementation) at every layer that touches the wire or a signature:

- BIP39/BIP32 key derivation (same mnemonic → same master key → same per-depth
  keypairs and addresses as sdk-js/sdk-python).
- The sha3-256 transaction signable hash and the JSON preimage it's computed over.
- ed25519 signing/verification.
- The passphrase-derived keystore encryption used to seal keypairs and master keys
  at rest.
- The `/v1` request/response JSON shapes themselves (including field order, which
  matters: `/v1` responses preserve key order so that "sign what you see" workflows
  are safe).

In practice this means: a mnemonic generated by sdk-js can be loaded into this SDK
with `FromSeed` (or vice versa) and will derive the identical keypairs and addresses,
and a transaction signed by any one of sdk-go/sdk-js/sdk-python is verifiable, and
spendable, by a node regardless of which SDK built it.

This is enforced by a shared set of golden test vectors
(`internal/testvectors/*.json`) generated directly from sdk-js's own internal crypto
primitives — this SDK's unit tests assert against those vectors, not against a
reimplementation of the same logic. See `internal/vectorgen/README.md` for how the
vectors are regenerated (they're produced by running `internal/vectorgen/gen.ts`
against an sdk-js checkout; this SDK's Go module never depends on sdk-js at build or
run time).

## Wire-compat integration test

`integration_test.go` (build-tagged `integration`) exercises this compatibility
guarantee against a live node instead of a golden vector: it builds a payment
transaction client-side, round-trips it through the node's
`POST /v1/transactions:serialize` and `POST /v1/transactions:deserialize` endpoints,
and asserts the deserialized transaction is identical to the one this SDK built.

It's skipped unless `LINEAGE_TEST_HOST` is set:

```bash
LINEAGE_TEST_HOST=http://localhost:3000 go test -tags=integration ./...
```

Without the tag (`go test ./...`, the default), this test file isn't even compiled
in.

## Not yet supported

Two-way (DRUID) payments are not yet implemented by this SDK. `DruidInfo` exists on
`CreateTransaction` for wire compatibility (so this SDK can read/round-trip
transactions that carry it), but there is no wallet-level API yet for constructing or
accepting a 2-way trade. See sdk-js/sdk-python for 2-way payment support via the
separate Valence service in the meantime.

## Testing

```bash
go test ./...                        # unit tests (fast, no network)
go test -tags=integration ./...      # + wire-compat integration test, needs LINEAGE_TEST_HOST
go vet ./...
```
